This specification was committed as b88096f and implemented through the seven-step build plan. Requirements below come only from the assignment sources; chosen architecture and unresolved interpretations are recorded separately under Open questions. The Check column preserves the original proposed checks; planning/validation.md maps requirements to implemented evidence and records the user’s acceptance of all 95 requirements. Planning-stage reviews below are retained as historical context.

Prerequisites were checked with `python3 tools/check_prerequisites.py`: all four checks passed and the command reported `READY`. The existing three starter tests passed with `API_KEY` unset; they do not verify the application requirements below.

## MVP review against supplied tests and JSON

This section records the design review performed before implementation; current validation is in planning/validation.md. The local-previous-work directory was excluded. All 20 request exports, the extraction schema, starter mock, starter tests and class verification instructions were inspected.

Observed checks:

- `env -u API_KEY python3 -m unittest discover -s tests -v` passed all three existing starter tests. They establish input loading, basic schema presence and offline canned-reply loading only; they do not establish application extraction, routing, provider handling, persistence or recovery.
- All 23 inspected input/schema/mock/hook JSON files decoded as UTF-8 with no duplicate object keys. Each of the 20 exports has the same five metadata/message keys and a nonblank message; messages contain 58–155 whitespace-delimited words.
- The schema has 14 required properties: 12 nullable scalar fields and two arrays, supporting_quotes and issues. Thus the chosen scalar exact-match denominator is 12 times 21 = 252. The earlier proposal of 273 was a counting error.
- tests/mock_responses/canned-reply.json is a startup example whose output_text is plain text, not a JSON extraction, and whose envelope has no completion status. Keep it for its starter test; create separate schema-conforming successful replies and provider failure/refusal/incomplete fixtures for the build plan.

The MVP fits these sample cases without a UI, server database or distributed scheduler. Its single-writer admission lock is a declared limit: a second mutating command receives a busy/retry response rather than processing concurrently; reviewers can still read completed work. This supports coherent overlapping operator use on one host, not multiple simultaneously active intake processes. A shared database read must capture its current queue and extraction data in one transaction.

Before implementation, the build plan must include dedicated fixtures/checks for complete facts, missing dates, conflicts, embedded instructions, provider errors, unchanged reruns, changed source, a fresh paraphrase, refusal, interrupted responses, and failure after success. Add operational cases for incremental batches, settings/policy refresh over stored sources, partial progress, two-process admission, process termination/resume, two filenames sharing one request ID, malformed exports, and interrupted export publication. The 20 supplied files alone do not exercise these operational sequences.

The schema enforces shape, not factual truth: it permits arbitrary date strings, unsupported names, omitted evidence through empty arrays, and an all-null extraction. Use local date/quote/completeness checks and independent source-derived expectations. In particular, valid supporting quotes do not prove that a scalar is supported or a conflict was preserved. Do not describe schema-valid output or passing mock fixtures as proof of hallucination-free live extraction.

Keep extraction fields separate from the outer processing record: document_id, source_sha256, status, owner, next_action, error and response_source do not belong inside the schema-conforming extraction object. The complete per-field source quotations and named provider envelopes still belong in the detailed build/test plan.
