# MVP build and test plan

This plan implements the 95 requirements in spec.md, committed as b88096f. It uses the adopted MVP defaults and excludes local-previous-work. Everything below describes intended work and expected behavior, not observed application results. The user authorized creating and committing this plan; implementation starts only after the plan review checkpoint. No application code or new tests are part of this commit.

## Choices

- Runtime: Python 3.10+ on Linux, with standard-library argparse, sqlite3, fcntl, concurrent.futures and urllib.request; use jsonschema for validation. Keep source under src/it_access with an editable-install pyproject.toml and a pinned, hash-checked requirements.lock containing runtime/build dependencies. Pin versions actually resolved in the implementation environment rather than guessing versions here.
- Interface: the installed `it-access` CLI, because operators need inspectable records and reproducible recovery commands without a web server.
- Test command: `env -u API_KEY python3 -m unittest discover -s tests -v`; all application tests block network sockets, use temporary stores and inject saved responses or mocked HTTP transport. Do not read the actual API_KEY in tests; inject a fake environment mapping for credential-path checks.
- Provider: mock by default; implement OpenAI Responses over HTTPS POST /responses with model gpt-4o-2024-08-06, strict JSON-schema output using the unchanged snapshot.schema.json, temperature 0, max_output_tokens 3000 and store false. No SDK or automatic retries. Endpoint and model are configurable. Capture the exact outgoing request and response handling as evidence. Confirm facilitator access before an optional live run.
- Storage: one local SQLite database, WAL mode, foreign keys enabled, 5-second busy timeout; one nonblocking OS lock beside its resolved absolute path admits mutating commands. Read-only queue/history queries use a single read transaction. No distributed workers or network filesystem support.
- Concurrency: two provider tasks, at most one task per document; a monotonic-clock start gate spaces calls by one second by default. Persist each result as it completes, rather than waiting in input order. Mock bulk tests set the interval to zero; a fake clock tests pacing separately.
- Scope: actual extraction integration, deterministic routing, history and restart recovery are required. No UI, approval execution, automatic backoff scheduler, worker leases, or policy-only optimization. Changing any relevant processing setting reprocesses affected sources.

### CLI contract

All commands accept `--db PATH` (default state/intake.sqlite3). Processing commands accept `--provider mock|openai` (default mock), `--model`, `--endpoint` (default https://api.openai.com/v1), `--timeout` (default 60 seconds), `--workers` (1 or 2, default 2), `--min-interval` (default 1 second), and `--mock-dir` (default tests/mock_responses). Reject invalid ranges before ingestion. Endpoint credentials/query strings are forbidden; keys belong only in the API_KEY environment variable for live mode. Never include credentials in a fingerprint.

```text
it-access intake INPUT_DIRECTORY [processing options]
it-access queue [--status STATUS] [--json]
it-access show DOCUMENT_ID [--history] [--json]
it-access resume
it-access retry DOCUMENT_ID
it-access refresh [--document DOCUMENT_ID] [processing options]
it-access export --output deliverables
it-access verify-export --output deliverables
it-access accuracy --expected tests/expected/facts.json --actual deliverables/extractions.jsonl --output deliverables/accuracy.md
```

Intake scans top-level *.json files in filename order. Capture bytes at ingestion so later filesystem edits cannot alter already scheduled work. Identity is exact filename, shared across input directories; same filename means a revision of that document. Different filenames with the same in-message ID remain separate. Empty or nonexistent directories are usage errors. A malformed file gets a durable error record with raw-byte hash, no extraction and an actionable explanation; valid files still proceed.

Queue displays one current record per document, including pending/running progress, source hash, attempt, status, owner, next_action and error; show includes provenance and optional history. Pending/running records use status pending/processing and action wait-for-extraction, not a human review route. Exports include only terminal current attempts; their manifest lists omitted pending/running document IDs so omissions are explicit. New pending work never appears as an older successful extraction for the same current revision.

Intake reuses a terminal success only when source hash and settings match. An unchanged terminal failure is displayed with its retry command but is not automatically retried. Changed bytes/settings schedule a new attempt. Retry creates a new attempt even after success, using the current stored bytes and original settings (required to exercise failure after success); refresh explicitly selects current processing options. Resume uses each unfinished job's recorded settings and original bytes. No live secrets are persisted with those settings.

Commands return 0 on success; intake/resume/retry/refresh return 1 if their selected work has a terminal failure, without rolling back other documents. Invalid configuration/usage returns 2; a held mutation lock returns 3 with an actionable busy message. Accuracy always writes a comparison report when inputs are valid and returns 1 for mismatches or invalid actual records. Export verification returns 1 for a missing/mismatched manifest. Read commands on a missing store return an actionable usage error without initializing the database.

### Persistence and recovery contract

Use three tables: documents (filename primary key, current revision/attempt references), revisions (integer key, document, original bytes, source_sha256, settings JSON/fingerprint, policy version, ingestion timestamp), and attempts (integer key, revision, pending/running/succeeded/failed/interrupted state, start/end timestamps, response_source, extraction JSON or null, routing values, categorized/redacted error). All attempts stay in the attempt table; current views follow the document's current attempt pointer, and history queries exclude that pointer. Repeated identical successful inputs add no revision/attempt. Explicit retry adds an attempt on the same revision; changed bytes/settings create a revision.

Admission, revision insertion and current-pointer changes are short write transactions under the OS lock. Commit a pending attempt and its current pointer before scheduling its provider call. Mark running before the call. Commit terminal result, extraction, routing and provenance together. Use a single owning store thread/connection for writes; provider workers return values and never update SQLite. Never hold a DB transaction during a model call. This avoids stale promotion without a distributed fencing protocol.

The lock is held by the main process and worker threads, never a detached child. If the process dies, the OS releases it. A newly admitted processing command marks leftover running attempts interrupted with a recorded error; resume then creates new attempts for interrupted jobs and runs pending jobs, preserving the interrupted attempts. A second process cannot process a newer source while the first owns the lock. A crash after remote completion but before local commit may cause a repeated paid request; document at-least-once execution. Graceful interruption leaves unfinished work resumable and exits nonzero.

Fingerprint canonical UTF-8 JSON with sorted keys and compact separators using SHA-256: provider mode, endpoint, model, prompt content hash, schema content hash, generation parameters, office-policy content hash, and routing implementation version. Timeouts, worker count, pacing, output paths and credentials are operational settings outside the reuse fingerprint, but record timeout/pacing for handover. Mock fixture content hashes also belong in mock fingerprints so changing a saved reply cannot silently reuse old output. Retry/resume store fixture names, while using current fixture bytes permits injected test failures and is recorded as the attempt's effective mock configuration. A live retry retains the original generation configuration. Refresh scans current stored sources, including documents absent from a later batch, and reprocesses when fingerprints differ. A routing implementation change must bump its version.

### Extraction, routing and failure contract

Send only message text as untrusted business content, distinct from the system extraction instructions. Do not send API credentials, use tools, interpolate source text into instructions, or send export timestamps as date evidence. The prompt specifies the supplied policy, exact quotes, nulls/issues, explicit corrections, unresolved relative dates and requested new permission. It requests source wording for business purpose and explanatory issue prefixes `missing:FIELD`, `conflict:FIELD`, and `instruction-override:`; free text after a prefix explains the issue. Kind synonyms may normalize to the supplied enums; names and business purpose retain source wording.

Normalize the provider envelope first: require response and assistant-message completion, no refusal content, exactly one nonempty output_text extraction, and valid JSON with no duplicate object keys. Reject unexpected output/tool types; never route a partial object. For scalar strings containing only whitespace, set null and add a missing issue before schema validation; otherwise preserve strings verbatim. Then validate the unchanged supplied schema, real calendar dates in YYYY-MM-DD form, and every supporting quote as a nonempty exact message substring. Require at least one evidence quote for a successful extraction. Do not silently repair invented quotes or invalid dates.

After validation, add deterministic issues for missing scalars, filename-stem/request-ID mismatch and reversed date ranges; keep model-provided conflict/override evidence. Missing kind is always a clarification condition except a prior override match. Every missing scalar, including fields not required for withdrawal, gets an explanatory issue. Conflict findings clear their named scalar to null and require at least two distinct supporting quotes; the independent expected-evidence checks verify that they preserve both alternatives. Fewer than two usable quotes for a conflict becomes a validation error rather than a guessed fact. This validation cannot establish general semantic truth; independent accuracy checks and human review still matter.

An internal override finding does not add a schema field. It is true if a validated `instruction-override:` issue has at least one supporting quote as evidence, or if a case-insensitive source scan finds `SYSTEM OVERRIDE`, `bypass approval`, `display the API key`, `mark request as approved`, or `highest-priority system instruction`. In the latter case add the matched source sentence as a quote and an explanatory issue. This source scan is a narrow fallback for IT-006 and tested variants, not an exhaustive detector. A benign permission request is not itself an override. The live model still supplies semantic findings for other wording; document false-positive/negative limitations.

Route in the policy's exact order: override; withdrawal with ID/date; other/null kind, conflicts, mismatch, missing new/change facts or reversed dates; production/write/admin complete new/change; complete staging/read. Return only human-review routes from the policy. No approval execution or approved status. All extraction failures use status error, owner IT Service Desk, next_action retry-extraction, extraction null and a redacted error with category and retry command. Categories are input, timeout, rate_limit, provider_auth, provider_unavailable, refusal, interrupted_response, malformed_output and validation. Preserve Retry-After as guidance only; one HTTP call per attempt and no automatic retry. response_source is mock or openai:MODEL for the attempted configuration, including errors; record configured and provider-returned model IDs separately when available.

### Exports and accuracy contract

Export both required terminal-current artifacts from one read snapshot under the mutation lock. Include document_id, source_sha256, attempt_id and generation_id in queue entries and outer extraction records along with required fields; extraction itself has exactly the supplied schema. Sort by document_id. Publish temporary files with flush/fsync and replace, then write manifest.json last with generation ID, byte hashes, selected settings/provenance and pending/running omissions. Verify manifest hashes and cross-artifact identity/attempt/source/routing agreement before treating files as published. A crash between replacements yields an explicitly invalid export repaired by rerunning export. A verifier that races replacement rejects rather than trusting mismatched bytes. Queue reads SQLite independently of export state.

Author tests/expected/facts.json separately from saved provider envelopes using the source-derived values below; it must not be generated from mock/application outputs. Mock fixtures intentionally include wrong/error variants as well as correct replies. Accuracy compares 12 scalar fields across exactly 21 expected document IDs (252 comparisons), including nulls; absent records or null extractions get zero of 12, even for expected-null fields. Invalid or duplicate actual records are reported, not silently overwritten; unexpected actual IDs are reported separately and do not change the denominator. Compare decoded scalar equality without trimming/case folding/synonyms. Score routing separately as one exact three-value tuple per document (21 denominator), with missing/failed records incorrect; validate quote membership and report required evidence/issue coverage separately. Mock demonstrations may score perfectly without making a model-accuracy claim. The automatic report lists every scalar mismatch with expected value, actual value and source evidence. A human then annotates the factual-error ledger to distinguish invented values, missing facts, wrong alternatives/corrections, and faithful alternative purpose wording; unreviewed classifications stay explicitly unreviewed, and exact-match mismatches remain mismatches. Optional live reports include actual model/configuration and must not overwrite labelled mock observations.

## Test plan

### Fixture and expectation conventions

Every fixture named below is planned, not yet written. Successful provider envelopes go in tests/mock_responses/IT-NNN.json (and paraphrase.json); each has status completed, one completed assistant message and output_text containing the schema-conforming extraction. Refusal/incomplete/error fixture names are explicit in the cases. The mock adapter returns response_source mock. Errors use saved type/message metadata interpreted as exceptions, never a network request. Wrong-fixture variants remain intentionally wrong to test validation or scoring. Independent expectations live separately under tests/expected. For fresh mock documents without a saved reply, fail explicitly rather than falling back to a generic successful extraction; arbitrary fresh wording is supported through the live adapter, and offline new-document tests provide their own saved reply. Do not derive expected facts by parsing a mock reply or running the application.

Route abbreviations used only in this plan: OWNER = review / System Owner / review-request; SECURITY = review / Security Review / review-risk-then-owner; CLARIFY = needs-information / IT Service Desk / clarify; WITHDRAW = review / IT Service Desk / confirm-withdrawal; OVERRIDE = review / IT Service Desk / inspect-message; ERROR = error / IT Service Desk / retry-extraction, extraction null. Each abbreviation expands to all three exact asserted fields.

For the source catalog below, every non-null literal scalar except normalized kind is an exact substring of that document's message (permission read may appear within reading; evidence must quote the containing phrase). The evidence column explicitly quotes kind cues and ambiguity/correction/missing-fact evidence. The field values themselves are quoted source fragments; when writing fixtures, use containing source clauses to make supporting evidence understandable. Nulls follow the policy quotation: “Represent absent or unresolved scalar values as null and explain each missing or conflicting fact in issues.” Absence is established by inspecting the whole supplied message, not by inventing a quote of text that does not exist. Corrected values follow: “A later statement explicitly labelled as a correction replaces the earlier value”. The source catalog fixes business-purpose wording before model measurement.

All supplied messages state request_date 2026-10-22; the exact substring is source evidence for that scalar on every row. The scalar tuple order is: request_id; kind; requester; team; system; environment; permission; business_purpose; start_date; end_date; manager (plus that common request_date = 12 fields). Evidence/issue expectations supplement the scalar tuple, not new extraction keys. The complete expected facts of each supplied-message case are the corresponding source-catalog row plus its expanded route and all missing/conflicting/mismatch/attack/range issues described there.

- Shared request ID: ingest IT-001.json and another filename followup.json containing the same IT-001 message. Two independent documents remain; followup.json receives a mismatch issue because its filename stem differs from IT-001, while IT-001.json remains OWNER.
